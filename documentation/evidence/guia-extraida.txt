1. Contexto, objetivos y resultados de aprendizaje
Las organizaciones almacenan operaciones en bases de datos relacionales. Estas estructuras suelen estar optimizadas para
registrar transacciones, pero no necesariamente para responder preguntas históricas, comparar períodos, analizar tendencias
o entrenar modelos predictivos.
El reto consiste en construir una plataforma que extraiga datos de una base relacional, los prepare en una zona intermedia
(staging), los cargue en un Data Warehouse dimensional y habilite análisis descriptivo, predicción, explicaciones y
notificaciones.
Objetivo general
Diseñar e implementar una solución integrada de ingeniería de datos y analítica inteligente que convierta datos operacionales
en información histórica confiable para Business Intelligence, Machine Learning y Generative AI.
Objetivos específicos
 1. Analizar una base relacional e identificar entidades, relaciones, reglas de negocio y oportunidades de análisis.
 2. Diseñar procesos de extracción inicial e incremental desde la fuente hacia staging.
 3. Aplicar perfilado, limpieza, estandarización, integración, validación y gestión de errores.
 4. Diseñar un modelo dimensional en SQL Server con hechos y dimensiones.
 5. Construir un dashboard web que consulte el Data Warehouse.

Manejo de nulos: guía de decisión
  No aplica: conservar NULL o un estado explícito si el modelo lo requiere.
  Desconocido: categoría controlada como 'Desconocido'; no confundir con cero.
  Pendiente: conservar el estado y permitir actualización posterior.
  Error de captura: corregir solo con regla confiable; de lo contrario, cuarentena.
  Medida numérica: no reemplazar automáticamente por cero; cero puede tener significado real.

5. Modelo dimensional y Data Warehouse
Star Schema y Snowflake Schema
Star Schema (esquema estrella): una tabla de hechos se relaciona directamente con dimensiones generalmente
desnormalizadas. Facilita comprensión y consultas.
Snowflake Schema (esquema copo de nieve): algunas dimensiones se normalizan en subdimensiones. Puede reducir
redundancia, pero aumenta la complejidad.
Recomendación: comenzar con Star Schema. Normalizar una dimensión solo si existe una razón concreta, como
reutilización, jerarquías o mantenimiento de atributos.
Proceso de diseño
 1. Seleccionar el proceso de negocio: ventas, compras o inventario.
 2. Declarar el grano: exactamente qué representa una fila. Ejemplo: una línea de orden de venta.
 3. Identificar dimensiones: quién, qué, cuándo, dónde y bajo qué condiciones.
 4. Identificar hechos: cantidades, importes, descuentos, costos u otras medidas.
 5. Definir claves sustitutas y conservar claves naturales para trazabilidad.
 6. Definir cambios históricos: SCD Tipo 1, Tipo 2 u otra estrategia justificada.
 7. Implementar y probar relaciones, grano y agregaciones.

Conceptos que deben demostrarse
  Granularidad: no mezclar una fila por orden con una fila por línea de orden.
  Medidas aditivas: sumables en todas las dimensiones, por ejemplo cantidad vendida.
  Semi-aditivas: sumables en algunas dimensiones, pero no en el tiempo, como saldo de inventario.
  No aditivas: ratios o porcentajes que deben recalcularse, no sumarse.
  Dimensión fecha: calendario, períodos y atributos de análisis.
  Dimensión desconocida: política para hechos sin dimensión correspondiente.
  SCD Tipo 1: sobrescribe el valor; Tipo 2: crea una versión nueva para preservar historia.

Carga y reconciliación
Resolver las claves de dimensión antes de insertar hechos. Evitar joins uno-a-muchos que multipliquen importes. Comparar
conteos y totales entre origen, staging y Data Warehouse, considerando filtros, rechazos y diferencias justificadas.
Entregables de esta etapa
  Diagrama dimensional editable.
  Documento de grano y definición de medidas.
  Diccionario de datos del Data Warehouse.
  Scripts SQL de creación, índices, constraints y cargas.
  Diseño de claves sustitutas y estrategia SCD.
  Consultas de reconciliación y resultados.

claramente como predicción y no como dato histórico.

  ¿Qué categorías tuvieron mayor crecimiento?
  Resume los principales cambios respecto al período anterior.
  ¿Qué regiones presentan una disminución relevante?

Arquitectura segura
Usuario → chat web → backend/API → validación de identidad y permisos → servicio analítico o consultas controladas →
resultados del Data Warehouse → modelo generativo → respuesta con contexto y fuentes.
El modelo no debe tener acceso irrestricto ni ejecutar SQL arbitrario con privilegios elevados. Preferir consultas
parametrizadas, vistas aprobadas o herramientas analíticas limitadas.

14. Recomendaciones finales y checklist
Errores frecuentes que deben evitarse
  Construir el dashboard antes de definir KPIs y modelo dimensional.
  Copiar tablas al DW sin declarar granularidad ni dimensiones.
  Reemplazar todos los nulos por cero sin entender su significado.
  Eliminar duplicados sin regla de supervivencia.
  Confundir un batch frecuente con tiempo real.
  Evaluar un modelo con los mismos datos de entrenamiento.
  Permitir que la IA genere cifras sin consultar una fuente autorizada.
  Conectar el frontend directamente a SQL Server.
  Entregar notebooks o diagramas sin scripts reproducibles.
  Presentar componentes aislados sin integración.

Checklist de entrega
  ■ Alcance y preguntas analíticas documentados.
  ■ Fuente identificada y ambiente reproducible.
  ■ ERD y diccionario de datos completos.
  ■ Staging conserva trazabilidad y separa raw de datos preparados.
  ■ Reglas de calidad documentadas y probadas.
  ■ Carga inicial e incremental, auditoría e idempotencia.
  ■ Data Warehouse con grano, hechos, dimensiones y claves definidos.
  ■ Resultados reconciliados con la fuente.
  ■ Dashboard consulta el DW y KPIs validados.
  ■ ML con baseline, métricas y prueba independiente.
  ■ GenAI consulta datos autorizados y reconoce límites.
  ■ Alertas disparadas y registradas.
  ■ README permite ejecutar la solución.
  ■ Repositorio libre de secretos.
  ■ Diagramas, manuales y resultados de pruebas entregados.
  ■ Video y demo funcional completos.
